# Комплект «рабочий из коробки» для RTX 5080: один бандл на две машины

Статус: 09.11.2026. Один комплект на оба целевых стенда; два профиля запуска, вторая сборка не нужна.
Зеркало EN-базы: `share-bundle.md`; цифры и ссылки на строки в обоих файлах одни и те же.

## Почему один комплект обслуживает оба стенда

Видеокарта на обеих машинах одна: RTX 5080, compute capability 12.0 (`sm_120`, Blackwell). Различаются
процессор (Intel Ultra 5 225F против Ryzen 7 9800X3D), память (64 ГиБ DDR5-6400 против 96 ГиБ) и диск
(около 14 700 МБ/с). Пакет движка несёт код по архитектурам, а не по машинам: `package_engine.py`
принимает `--arch` повторно (`action="append"`, package_engine.py:304) и пишет список в
`engine-component.json` (schema 2: SHA-256 и размер каждого файла, package_engine.py:11, :219-222).
Поэтому один CUDA-пакет, собранный с `--arch sm_120`, работает на обеих машинах.

Тулчейн определяется картой, а не машиной: `cuda_choice()` оставляет карты RTX 50 на CUDA 13, потому
что движки CUDA 12.8 для `sm_120` падали на длинных промптах (#220, setup.py:1948-1959). Сам CUDA 13
компилирует для `sm_75` и новее (setup.py:262, `CUDA13_MIN_ARCH = 75`), а релизные рецепты апстрима уже
несут строку архитектур `"75;86;89;120"` (setup.py:2088-2090). Значит для этих двух машин комплект -
это «CUDA 13, arch 120»; добавлять в тот же пакет другие архитектуры нужно только ради чужих карт, и
это стоит времени сборки в `package_engine.py` (PTX через `compute_*` - по желанию).

CI каналом поставки такого комплекта не является, и ожидание «CI для всех конфигураций» готового
комплекта не даёт: это написано в самом workflow бэкендов - «Architectures are fewer than the release
package's (compile time)» (.github/workflows/backends.yml:10), - а артефакты workflow оставляют только
при падении (`upload-artifact` под `if: ${{ failure() }}`, check.yml:101-109 и :144-152,
snapshot.yml:77-83) с `retention-days: 7`. В форке прогоны ещё и ждут одобрения мейнтейнера, поэтому
CI не может быть способом передать готовый пакет другому человеку.

## Сборка комплекта

1. Собрать движок под `sm_120` с CUDA 13. Текущий оконный рецепт жёстко стоит на `sm_86` и на тулчейне
   из `CUDA_DIR` (файл лежит вне этого репозитория движка: `../harness/scripts/build_strata.bat` в дереве
   Страты), поэтому для комплекта он не годится: нужна сборка
   с CUDA 13 и `sm_120` (плюс `compute_89`, если нужен PTX-запасной путь). Здесь ничего не собирается:
   обёртка принимает уже готовую папку сборки.
2. Собрать комплект, сначала только показать вызовы:

```
python packaging/make_share_bundle.py --build <папка сборки со strata.exe> --archs 120 --cuda 13 \
    --platform windows-x86_64 --version 0.1.45 --out FEED --keys KEYDIR \
    --url http://<эта машина>:8099 [--terminal strata-terminal-0.1.45-windows-x86_64.zip] --dry-run
```

   Без `--dry-run` то же самое выполняется по-настоящему. Обёртка отказывает (код 2): папке сборки без
   `strata.exe`, пустому `--archs` (пустой список - это «проверка не состоялась», а не «ок»), CUDA 12 с
   `sm_120` (со ссылкой на setup.py:1948-1959 и #220) и CUDA 13 ниже `sm_75` (setup.py:262). Затем она
   вызывает два уже существующих упаковщика и не повторяет их логику:

   * `packaging/package_engine.py` - один CUDA-пакет с `engine-component.json`;
   * `packaging/make_local_feed.py` - локальный фид с тест-подписью: `strata-feed.json` + `.sig`,
     члены `control/` и `engine/`, `install-manifest.txt`, `install.sh`, `install.ps1` с подставленным
     адресом `--url`, и `test-trust.json` (публичный тестовый ключ).

3. Раздать фид:

```
python -m http.server 8099 --bind 0.0.0.0 --directory FEED
```

Без `--terminal` в фиде нет control-пакета: `install.ps1` тогда нечего ставить первым, поэтому архив
терминала надо передать, если человеку нужны `strata update` и `strata launch`.

## Что получает человек на другой стороне

* `install.ps1` - одной строкой, адрес фида уже внутри.
* `strata update` - забирает пакет движка из этого фида; доверие - через
  `STRATA_UPDATE_TRUSTED_KEYS=<FEED>/test-trust.json` (тестовый ключ, для пробного прогона годится).
* `strata launch` - запускает движок из установленного компонента.

Тестовый ключ существует только для такого прогона: настоящий релиз подписывается релизным ключом,
который никогда не покидает папку ключей (make_local_feed.py:11-16). Не передавать `test-trust.json`
как производственный ключ.

## Модели в комплект не входят

Файлы GGUF весят десятки ГиБ, поэтому комплект не несёт их, а перечисляет: человек скачивает сам
оттуда же, откуда брали мы. Записи, уже закреплённые в `setup.py` (имя, байты, SHA-256; в файле две
формы записи - `("ple", байты, sha)` и `(байты, sha)`):

| файл | байт | SHA-256 |
| --- | ---: | --- |
| ple-fp8.gguf | 51 200 246 176 | `37f89b8ce5a3425932763257c40229ec02723ad2ab14b4bbfc26a486f4725c9c` |
| Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf | 22 853 663 008 | `55983c5a75a1ab969824077b3bb3de4146e82a9234072b48ad4e8f92ad3fe9f1` |
| Qwen3.6-35B-A3B-UD-Q6_K_XL.gguf | 32 611 711 264 | `35fce994cd36104a7dc1bd8a4bdf13778145664c00fdef6773aebc9246e5019c` |
| Qwen3.6-35B-A3B-Q8_0.gguf | 37 801 097 504 | `c1283d8b80c3e38b2735ddbc9766d3b3126f44d6c484be419d4e101d09a76131` |

Полный закреплённый список - в `setup.py` (искать `.gguf":`). Модели, на которых снимались наши замеры
(KAT IQ4_XS, heretic Q4_K_M, HauhauCS IQ4_XS), лежат локально и в `setup.py` **не** перечислены: кто
повторяет наши числа, должен добыть те же файлы и сам сверить их SHA-256.

## Честная оговорка: профили тюнинга не для этого железа

Все наши числа профилей сняты на RTX 3060 Ti 8 ГиБ, 4-ядерном i7-4790K, 32 ГиБ DDR3 и диске `D:`, а
не на RTX 5080 с 20-поточным процессором и 64-96 ГиБ памяти. На целевых машинах ничего из этого не
перемерялось. Рычаги придётся снимать заново:

* `--n-cpu-moe` (сколько слоёв экспертов остаётся в памяти хоста) - на 16 ГиБ видеопамяти он будет
  заметно ниже наших 30-33 для 8 ГиБ;
* `-ub` и `-b` (физический чанк) - наши 2048 здесь следствие зажима от `-b 2048`, а не универсальное
  значение;
* `att-mb` (рабочая память attention) и `--vram-reserve-mib` (запас видеопамяти) - оба подбирались под
  карту, где узким местом был свободный объём VRAM;
* super-chunk N (у нас N=4), глубина MTP (у нас 2), FA вкл/выкл - последние два меняют вывод только
  через режим сэмплинга и мерялись на другом поколении GPU.

## Два каркаса профилей (заглушки, НЕ числа)

Каждое значение равно `null` намеренно: каркас - не замер. Заполнять только после прогона на целевой
машине и рядом с числом писать, откуда оно.

```json
{
  "_comment": "NOT MEASURED ON THIS HARDWARE - placeholders only",
  "target": "Intel Ultra 5 225F + RTX 5080 16 GB + 64 GiB DDR5-6400",
  "model": "<pick from the GGUF list>",
  "ctx": null,
  "batch": null,
  "ub": null,
  "ncmoe": null,
  "att_mb": null,
  "vram_reserve_mib": null,
  "super_chunk": null,
  "mtp": null,
  "fa": null
}
```

```json
{
  "_comment": "NOT MEASURED ON THIS HARDWARE - placeholders only",
  "target": "AMD Ryzen 7 9800X3D + RTX 5080 16 GB + 96 GiB RAM + SSD ~14700 MB/s",
  "model": "<pick from the GGUF list>",
  "ctx": null,
  "batch": null,
  "ub": null,
  "ncmoe": null,
  "att_mb": null,
  "vram_reserve_mib": null,
  "super_chunk": null,
  "mtp": null,
  "fa": null
}
```

Более быстрый диск второй машины важен только для загрузки модели и файлового режима; после того как
модель уже в памяти, профиль, упирающийся в VRAM, быстрее не становится.
