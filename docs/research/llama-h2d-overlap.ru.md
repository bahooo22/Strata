# Перекрыть H2D экспертов с вычислениями (llama.cpp)

**Статус:** дизайн. Требует правки планировщика; это не параметр.

## Где

- `llama.cpp/ggml/src/ggml-backend.cpp:1693-1793`: для `MUL_MAT_ID`, чьи веса в host-буфере,
  копируются только используемые эксперты, сгруппированные по подряд идущим id. Перед
  копиями планировщик вызывает `ggml_backend_synchronize(input_backend)` (1705); копии
  идут через `ggml_backend_tensor_set_async` в целевой backend.
- `ggml-backend.cpp:1401-1412`: один буфер копий на backend (`cur_copy`) — единственная
  staging-область.
- `llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu:2445-2450`: `set_tensor_async` ставит H2D
  в вычислительный stream backend'а.
- `llama.cpp/src/llama-context.cpp:247, 3436-3439`: граф режется на ubatch'и; планировщик
  копирует входы узла прямо перед его запуском.

Следствие: копии и ядра MMQ делят один stream и один буфер, поэтому H2D слоя не может
идти, пока считается предыдущий слой.

## Дизайн

1. Отдельный copy-stream в CUDA backend (`cudaStreamCreateWithFlags(nonBlocking)`).
2. Второй staging-буфер для весов `MUL_MAT_ID` (двойная буферизация); `+0.9 ГиБ` VRAM
   для этой модели (0.42 ГиБ на слой).
3. Перекрытие внутри слоя. Ids слоя появляются только после его роутера, поэтому копии
   gate/up этого слоя раньше начать нельзя. Перекрывать можно копию down-экспертов: она
   идёт в copy-stream, пока занят MMQ gate/up (примерно треть трафика слоя). Заглядывание
   на слой L+1 невозможно без переупорядочивания: ids L+1 зависят от выхода слоя L.
4. Сами ids — device-тензоры; D2H крошечного тензора ids можно пустить в copy-stream
   со своим event (сегодня это синхронный get, `ggml-backend.cpp:1725-1728`).
5. Оставить текущий путь как fallback, когда буфер не выделяется или графы выключены
   (`ggml-cuda.cu:2569-2580` отключает графы для синхронного fallback).

## Ожидаемый эффект

Промптный путь копирует ~0.42 ГиБ на слой; при 22–26 ГБ/с (pinned) это ~17 мс на слой,
~450 мс на 26 слоёв против ~140 с prefill 128k — выигрыш даёт снятие синхронизации на
слое и перекрытие копии down с MMQ gate/up, а не одна лишь пропускная способность.
Верхняя граница в терминах замера: **pp +8–20 %** (прежние +15–35 % предполагали
заглядывание на слой, которое зависимость ids исключает).

**Оговорка для 8 ГБ.** Второй staging-буфер стоит ~0.9 ГиБ. На этой карте 128k уже
занимает ~7.5 ГиБ, поэтому overlap возможен только с меньшим окном (96k), со снижением
`ncmoe` на 1–2 слоя (~0.4 ГиБ каждый) или с меньшим `-ub`. Сначала измерить запас VRAM;
иначе патч превращает OOM в фичу.

## Замер на референсной машине (03.11)

С `GGML_MOE_TRACE=1` на прогоне 128k (fill 117 753, pinned, `-ub 8192`, `ncmoe 30`):
5220 вызовов копий экспертов по 90 узлам, скопировано **660.8 ГиБ**; при 22–26 ГБ/с это
**27–32 с H2D внутри prefill 142 с (~20 %)**. Полное перекрытие может вернуть максимум
около 20 % pp; реалистичная цель для дизайна выше — +8–15 %.

## Риски

- Ошибки порядка stream'ов молчаливы и зависят от данных; каждый переиспользуемый буфер
  должен быть защищён event'ом.
- CUDA-графы захватывают stream'ы и event'ы; патченный путь либо должен поддерживать
  захват, либо работать без графов.
- Лишняя VRAM может увести плотную раскладку в OOM; fallback обязателен.
