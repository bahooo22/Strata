# Аудит форка: где на самом деле теряется время (RU)

**Статус:** аудит кода плюс измерения заказчика. Вердикт: узкое место не в GPU-ядрах, а в
доставке весов экспертов; измеренный рычаг — размер чанка prefill; переход движка на
upstream master — no-go.

## Предмет и метод

Разбирались две части форка: движок `engine/` (ветка `engine-on-master`) и форк llama.cpp
`llama-master` (ветка `h2d-hooks`, `2a7086597` = upstream master `149f5641b` плюс
upload-stream, `GGML_SCHED_COPIES` и D2D-трассировка).

Три зоны: декод и KV, оркестр prefill, собственные CUDA-ядра движка. Плюс отдельно —
MMQ-диспетчер движка, патчи форка llama и специфика машины.

Ограничения: аудит только на чтение — ни одной сборки, ни одного прогона на GPU, ни
одного изменения в чужих деревьях. Все числа ниже либо измерены заказчиком (помечено
«замер»), либо посчитаны по формулам самого кода (помечено «расчёт»). Полные отчёты с
якорями лежат вне проекта: `glm\2026-11-04_session\strata-master\`.

## Что важно знать про ветку кода

Замеры «pp 568-584 на 96k» — это **не** `src/prefill/prefill.cpp`, а отдельный движок
`src/qwen35/q36_engine.cu` (`strata-q36`): `src/program/generate.cpp:3271-3283` уводит
файл с архитектурой `qwen35moe` в `strata::qwen35::run()`.

- `src/prefill/prefill.cpp` обслуживает другое семейство (геометрия зашита в `:207`:
  `N = 2560, HC = 4, K = 10, NE = 512` — топ-10 и 512 экспертов);
- `src/split/*` — третий независимый движок `fnx` (мульти-GPU);
- ветка `qwen4exp` (`src/core/*`, `src/spec/*`, постраничный KV `kv_q4.cu`/`kv_q8.cu`) —
  путь для Qwen3.8-Flash-Next: 37.6-54.8 ГБ RAM+VRAM (по `docs/MODELS.md:38-48`), то есть
  на 8 ГБ VRAM и 32 ГиБ RAM он не идёт.

Вывод для чтения отчётов: находки по `prefill.cpp` и `split/*` к замерам 96k не
переносятся, а ветка `qwen4exp` на этой машине вообще не исполняется.

## Зона 1: декод и KV

**Декод упирается в полосу RAM хоста, а не в GPU** (расчёт по `q36_engine.cu:2623`):
CPU-пул читает из RAM около 41 слоя × 8 выборов × (1−S/256) × 1.63 МБ ≈ **487 МБ весов
экспертов на токен** — это 26-35 мс из ~45 мс/токен при полосе RAM 15-20 ГБ/с. GPU за
это время успевает ~1-1.4 ГБ трафика (2.5-3 мс) и простаивает. Значит GPU-оптимизации
декода дают единицы процентов; лечится это числом резидентных слотов, квантом экспертов
на хосте или перекрытием CPU и GPU.

| что | где | ожидание | класс |
| --- | --- | --- | --- |
| MTP-блок занимает слоты, VRAM и RAM **даже при `--mtp 0`**: 2.4 % слотов экспертов, ~0.4 ГБ RAM, 1/11 KV | `q36_engine.cu:1244-1245`, `:3181-3183`, `:3304-3305`, `:1548-1562` | прямое освобождение места под экспертов | только их ПК |
| гибрид (attention + SSM) **отключает CUDA-граф** — около 800 запусков ядер на токен | `q36_engine.cu:3271` | крупный, но требует разбора: можно ли включить граф при гибриде | всеобщий |
| слоты экспертов съедают не-KV буферы: staging 834 МБ, `k16`/`v16` 201-268 МБ, буфер скоров 384 МБ, `router_ext` 86 МБ; каждый +8k окна ≈ 4.3 слота эксперта на слой | `q36_engine.cu:3275`, `:1400`+`:1637`, `:1638-1639`, `:1635`, `:1275-1279` | освобождение VRAM = больше слотов = меньше чтений с RAM | только их ПК |
| split-K внимание читает KV в 8 раз больше нужного из-за GQA, и `q4_0` деквантируется побайтово | `q36_engine.cu:2295-2300`, `:475`, `:344-386` | 1-3 мс/токен на 96k | всеобщий |
| сериализация GPU↔CPU-пул по 41 слою; busy-wait `cudaEventQuery` 41 раз на токен; двойное квантование активации (GPU `:1964` и хост `:2617`) | `q36_engine.cu:2578-2639`, `:2596-2597` | нет перекрытия CPU и GPU | всеобщий |
| **нет Уолша-Хадамарда для `q4_0`-KV**, хотя код уже есть в `kv_q4.cu:25-69` | `q36_engine.cu:294-386` | не ускорение, а качество: измеренная деградация `q4_0` — 62 совпавших символа с fp32 против 471 у `q8_0` | всеобщий |

Маршрутизация проблемой не является: top-k и группировка слиты в один запуск
(`q36_kernels.cuh:309-397`), повторного расчёта нет.

## Зона 2: оркестр prefill

**Около 806 ГБ H2D за промпт** (расчёт: 46 чанков × 16.34 ГиБ; при `h2d_gbps = 12.0`,
константа проекта в `include/strata/program/prefill_plan.hpp:36`, это 65-80 с из ~160 с
TTFT). Причина: чанко-мажорный префилл — каждый чанк заново копирует в VRAM весь набор
экспертов каждого слоя (`q36_engine.cu:2418-2423` → `:2536`).

| что | где | ожидание | класс |
| --- | --- | --- | --- |
| правило чанка — жёсткая лестница по свободной VRAM, 4096 автоматически не выбирается | `q36_engine.cu:4275-4281` | измерено, см. ниже | всеобщий |
| **super-chunk прогона нет**, хотя в соседнем движке он есть («the layer's experts are staged ONCE for every sub-chunk of the super-chunk») | `q36_engine.cu:2418-2423` против `prefill.cpp:6585`, `:6595`, `:6619` | в 4 раза меньше байт по PCIe без роста буферов MMQ; риск высокий (нужен стейт всех слоёв сразу) | всеобщий |
| на WDDM `cudaEventRecord`/wait ≈ 80/45 мкс против ≈ 3/0 на Linux, одно событие на каждого стримуемого эксперта (≈480 тыс. записей и ожиданий за промпт); средства `STRATA_PREFILL_COPY_EVENT_EVERY` и `STRATA_PREFILL_COPY_WAIT_DEDUPE` **выключены по умолчанию** | `prefill.cpp:3702-3705`, `:3749-3756`, `:3806-3851`, `:3869-3881` | от единиц до десятков процентов | только Windows |
| модель планировщика, которая считает H2D и промахи page cache, **не подключена** — реальный скан смотрит только на VRAM | `include/strata/program/prefill_plan.hpp:81-128` (вызовов нет) против `generate.cpp:9335-9400` | потенциально крупный | всеобщий |
| экспертный блоб копируется дважды: `pread` в pinned-буфер → DMA в VRAM; при 16.34 ГиБ экспертов набор в page cache (32 ГиБ RAM) не помещается → каждый чанк перечитывает его с диска | `expert_source.cpp:2053-2057`, `expert_cache.cpp:797` | RAM-тир на стороне q36 уже дал +73 % | только их ПК |
| ветка «весь слой с host» пересчитывает и те 23-37 экспертов, что уже в VRAM-слотах; в комментарии кода — **противоположный** замер (whole 1970 против runs 1540) | `q36_engine.cu:2535-2553` | единицы процентов, нужен перезамер | всеобщий |
| барьер на слой тянет и `rmax` (нужен для выбора тайла MMQ), и `rcnt` (нужен только для счёта роутинга) | `q36_engine.cu:2339-2343` | мал на hybrid; снимается целиком в раскладке «всё в VRAM» | всеобщий |
| weight-stationary скомпилирован, но `mode()` требует cc 6.0 → на их карте всегда выключен | `src/prefill/moe_ws.cu:57-71` | рычага на 3060 Ti нет | — |

## Зона 3: собственные CUDA-ядра

**Ни один из аудируемых файлов не исполняется в prompt-режиме** на их стенке:

- `moe_ws*.cu` — `moe_ws.cu:57-67` требует cc 6.0 у всех видимых GPU, поэтому `mode()`
  всегда 0; кроме того, `CMakeLists.txt:2306` собирает их только при
  `STRATA_EXPERIMENTAL_SM60`, а CUDA 13 для sm_60 не годится;
- `moe_fused_iq.cu` — `gu_covered()` (`:1873-1881`) покрывает `Q4_K` и `Q5_K` только на HIP
  gfx11; на CUDA их пак не покрыт ни при каких флагах;
- `native_gdn.cu`, `fused_gdn.cu`, `native_bf16.cu` — qwen35-движок считает GDN своими
  `k_gdn_seq` и `k_gdn_seq_cols`, а `fused_gdn_conv_l2` прямо запрещён
  (`q36_engine.cu:2191`);
- `iq_kernels.cu` живёт, но обслуживает qwen35-декод, а не prompt (prompt идёт через
  `MMQ::Context::run`).

Это совпадает с их замером `docs/profile-q36.md`: 91 % времени в MoE, из них 71 % на
CPU-пуле, и ×1.7 по prompt дала pinned host-арена, а не код ядер.

Что реально лежит на их пути и проверяется без переписывания кода:

- `STRATA_KQ_SPLIT` **не включён** (`iq_kernels.cu:908-910`): их `Q4_K` и `Q5_K`-эксперты в
  qwen35-декоде декодируют вес на каждый столбец вместо раза на 4. Флаг побитово нейтрален
  (проверяется `iq_multi_parity`), в таблице дефолтов sm_86 его нет;
- `STRATA_OLD_IQ_MMVQ` (`iq_kernels.cu:3417`) держит в бинарнике заведомо худший путь;
- геометрия 2560/640/80 зашита: `row_dot_80_sub16`, `native_gu_swiglu_kernel`, `expdec`,
  S26 и S27 недостижимы при их 2048×512; `STRATA_GU_SWIGLU=1` горит по дефолту, но код его
  не берёт (проверка — `cuobjdump` по символам);
- `native_gdn.cu` читает state с шагом 24 КБ между lane'ами (`iq_kernels.cu:60`, `:62`,
  `:81-82`) — 8-кратное раздувание трафика; в `fused_gdn.cu` тот же state читается
  коалесцированно.

## MMQ-диспетчер, патчи форка llama и машина

- **Слитый swiglu + квантование заблокирован гейтом по архитектуре**: `moe_mmq.cu:152`,
  `:836`, `:846` — `STRATA_EXPERIMENTAL_SM60` (сборка для Pascal/Volta). На их карте
  (cc 8.6) не собирается вовсе, хотя движок путь умеет и умеет включать (`prefill.cpp:5086`,
  `:5817`) — условие просто всегда ложно. Комментарий автора: путь битово тот же. Эффект:
  минус чтение 1280 float и запись 640 float на строку на группу, минус буфер `H_g` в VRAM.
- **Расхождение ширины экспертной строки**: в движке 640 (`prefill.cpp:5302`, `:5311`;
  `moe_mmq.cu:111` — «codes [1280][640 B]»), в карточке модели `expert_feed_forward_length
  = 512`. Если 640 — паддинг, MMQ считает на 25 % лишних строк на слое. Проверяется без
  правок: `mmq_expert_bench` печатает `R` в каждой форме.
- **RAM на пределе**: 32 ГиБ = файл модели 17-23 ГиБ в файловом кэше Windows + safety
  headroom 8 ГиБ на Windows (`ple_residency_test.cpp:80-87`), и только потом остаётся место
  под арену. При нехватке движок пишет «Free RAM or lower STRATA_RESIDENT_HEADROOM_GIB»
  (`expert_source.cpp:4201-4204`) — если эта строка есть, часть экспертов идёт с диска.
  Кандидаты: `STRATA_UNBUFFERED_LOAD=1`, `--ram-keep-gib`, `STRATA_RESIDENT_HEADROOM_GIB`.
- **Их upload-stream на 8 ГиБ и PCIe 3.0 упирается в блокировку хоста**: кольцо на 64
  слота обходится за один проход графа, поэтому слот занят чаще, чем хост успевает;
  `GGML_SCHED_COPIES` отсечён по памяти (`n_copies=2` давал 25 777 МиБ). Оба патка — только
  для llama-профилей: движок не компилирует `ggml-cuda.cu` и не пользуется
  `ggml_backend_sched`.
- **Уточнение по машине**: RTX 3060 Ti — это GA104, то есть **Ampere**, cc 8.6, 38 SM,
  100 КиБ разделяемой памяти на блок; int8 tensor cores (`mma.m16n8k32` с s8) и `cp.async`
  есть — это видно по их коду (`src/prefill/moe_fused.cu:182-218`: ветка `__CUDA_ARCH__ >=
  800`, а ветка `>= 750` помечена у них как Turing).

## Измерено: размер чанка prefill

Замер заказчика на 96k (KAT IQ4_XS, окно 96k, тот же сценарий bench_dialog):

| chunk | pp | tg | экспертных слотов на слой |
| --- | ---: | ---: | ---: |
| 1024 (было) | 573.8 | 21.4 | 23 |
| **2048** | **1094.3** | 20.6-21.7 | 18 |
| 4096 | 1608 | 17.3-19.7 | 3 |

На 128k верхняя точка — 2048: при 4096 в VRAM не остаётся ни одного слота экспертов
(«0 of 256» в логе), весь MoE уходит на CPU, и 128k даёт 586.2 pp против 648.3 при 2048.

Механика выигрыша: сокращается не только трафик, но и **число полных обходов всех 41
слоя** — каждый чанк заново проходит по всем слоям экспертов. Поэтому выигрыш не
складывается с долей PCIe-трафика, а умножается на число слоёв. Цена — decode и число
экспертных слотов: освободившуюся VRAM съедают буферы MMQ под больший чанк.

## Переход движка на upstream master: no-go

| точка | база `3cf03257` | `engine-on-master` | дельта |
| --- | ---: | ---: | ---: |
| 96k bench | 573.8 / 21.4 | 587.7 / 22.4 | +2.4 % pp, +4.7 % tg |
| 128k live | 648.3 / 14.0 | 512.2 / 14.8 | **-21 % pp** |
| serve A/B decode | 26-28 tok/s | 24-27 tok/s | хуже |

Причины по коду: переход приносит API master (`J_best`, `prec_src1`) и его тайловые
решения, а у Страты своя раскладка экспертов (640 против 512, см. выше); на 128k, где
слоёв много, а чанков мало, это и стоит 21 %. Слияние gate/up в MMQ (fused) эффекта не
дало (586.4 против 587.7): у Страты gate и up уже считаются одним запуском, тогда как на
llama-пути их два, и именно снятие второго запуска даёт там +7.2-8.5 % pp.

## Что делать по порядку

1. **Размер чанка** — единственный измеренный рычаг, правок не требует: `STRATA_Q36_CHUNK`
   для 96k, для 128k — не выше 2048.
2. **Слоты экспертов** — теперь главный дефицит: MTP при `--mtp 0` (2.4 % слотов),
   `STRATA_Q36_ATT_MB=64`, `--vram-reserve-mib 512`, отказ от `k16`/`v16` для длинных
   окон. Каждый освобождённый ГиБ ≈ 1.6 % трафика.
3. **super-chunk** — в 4 раза меньше байт по PCIe, но риск высокий: нужен рекуррентный
   стейт всех слоёв сразу.
4. **Слитый swiglu + квантование** — снять гейт `STRATA_EXPERIMENTAL_SM60` с
   `moe_mmq.cu:152`, `:836`, `:846` и перевести основную ветку prefill на слитый вызов
   (`prefill.cpp:5311-5315`, `:5391-5395`) там, где нет Hadamard по `H_g`. Числа должны
   совпасть.
5. **Ширина экспертной строки** — замер `R` в формах `mmq_expert_bench`: если 640 вместо
   512, это +25 % работы в MMQ, и вопрос упирается в формат кодов, а не в код.
6. **WDDM-события** — `STRATA_PREFILL_COPY_EVENT_EVERY=16` и
   `STRATA_PREFILL_COPY_WAIT_DEDUPE=1` (для контура strata, не q36).
7. **KQ-split и старый MMVQ** — `STRATA_KQ_SPLIT=1` (декод K-квантов), побитовая нейтральность
   проверяется `iq_multi_parity`.
