### `2fdbdb56d8a6` — fix(setup): make the install folder before writing a run config into it (#7012)

- Дата: 2026-11-24
- Автор: Niko1221
- Файлы:
  - `terminal/setup.py` (+6/-1)
  - `terminal/strata_cli/cli.py` (+4/-0)
  - `terminal/tools/test_setup_config.py` (+56/-0)

- Связанные решения:
  - `setup-install-folder`: upstream — Create the Terminal install folder before the first config/run script.
  - `setup-hip-ram-slack`: upstream — HIP card+RAM plan without SSD gets bounded RAM slack; other backends unchanged.
  - `qwen36-catalog-preserve`: ours — Fork KAT/Huihui IQ4_XS catalog entries are absent upstream and preserved in the predicted tree.

**Исходное сообщение commit**

```
A fresh Terminal-only Linux install stopped after the engine step with
FileNotFoundError on ~/.local/share/strata/install/strata-<model>.json.tmp:
write_config wrote <path>.tmp without making the parent folder.

Why the folder was missing: `strata install` (strata_cli/cli.py _install) runs
setup.py with STRATA_CONTROL_INSTALL=1 and STRATA_INSTALL_DIR=install_root(),
which is only a path (the discovery.find_install default,
<data home>/strata/install) and nothing made it on that route. setup.py's
home() is that folder. Before the first run config the install only makes the
data folder beside it (<data home>/strata/Strata-data, with parents) and the
model folders, so `strata` existed but `install` did not. `strata launch` is
not affected (Catalog.__init__ makes its root), and a full checkout writes into
ROOT, which exists. A custom --data-dir does not matter: the run configs follow
STRATA_INSTALL_DIR, not the data folder.

Fix: write_config makes the parent folder (mkdir parents, exist_ok) before the
.tmp write; write_run_script (run-*.bat / .sh) makes home() the same way; and
`strata install` makes STRATA_INSTALL_DIR before handing over to setup.py.
The .bak copy in write_setup_config only runs when the config file exists, so
its folder exists; the other writers (settings.json, the data
and models folders) already make their own folders.

Tests: tools/test_setup_config.py MissingInstallFolder (write_config with a
Path and a str, write_setup_config for a first install and over an earlier
config, write_run_script) into a folder whose parents do not exist; all five
fail on the old code.
```

  - `hip-kv-window-choice`: upstream — HIP plans a 32K K/V window and the selected K/V type; CUDA/SYCL/Metal behavior stays.
  - `qwen36-catalog-preserve`: ours — Fork KAT/Huihui IQ4_XS catalog entries are absent upstream and preserved in the predicted tree.
  - `fork-planner-base`: ours — Fork CUDA/desktop/RAM planner constants remain; upstream HIP window is additive.
  - `upstream-tests`: upstream — Accept upstream regression coverage without deleting existing fork tests.

**Исходное сообщение commit**

```
0.2.21 names the backend in setup's plan (hip), and for hip the planner put the whole context's global K/V on the card, times the 1.6
growth margin, in FP16: an RX 9070 XT (16 GB) with SQ-15 planned 3.94 GiB of experts at 128K and none at 256K (0.2.20: 11.10 at 128K).
Experts that do not fit run on the CPU, the slowest part of a hybrid token.

The HIP engine does not allocate the K/V that way. Its pools start empty and take pages on demand (ink_hip_backend.hip.cpp ensure_page); when the
pool grows it doubles, steps by 32 pages under 1.5 GiB free, and when the card is full it moves the pool to host-mapped pinned memory
("KV pool VRAM tight ... spilled to host-mapped pinned KV", grow_pool). The drafter K/V grows the same way (ensure_dspark_slot_cap). Without a
--vram-experts-gb the engine itself counts only 4096 tokens a slot. A longer chat is slower once the K/V has spilled; it does not fail.

non_expert_gb() on backend hip now counts the global K/V and the drafter K/V for min(ctx, 32768) tokens a slot (HIP_KV_WINDOW_TOKENS). 8K and 32K
plan as before. The unified-memory path (compute_unified: Strix Halo, iGPU, where the K/V sits in the same memory) and every other backend are not
touched.

setup also tells the HIP plan the K/V type of --kv fp8 / fp16 (inkling_plan_kv); the plan assumed FP16 above 13 GiB whatever was asked, twice the K/V
of an fp8 start. Other backends get the call they always got.

Tests: test_inkling_fit_hip_window.py (11).
```

### `2ddda80a6c19` — fix(launch): give the RAM cap of a HIP card + RAM plan with no SSD tier some room

- Дата: 2026-11-24
- Автор: Niko1221
- Файлы:
  - `terminal/setup.py` (+21/-3)
  - `terminal/tests/terminal/test_inkling_fit_free.py` (+41/-1)

  - `setup-install-folder`: upstream — Create the Terminal install folder before the first config/run script.
  - `setup-hip-ram-slack`: upstream — HIP card+RAM plan without SSD gets bounded RAM slack; other backends unchanged.
  - `qwen36-catalog-preserve`: ours — Fork KAT/Huihui IQ4_XS catalog entries are absent upstream and preserved in the predicted tree.
  - `upstream-tests`: upstream — Accept upstream regression coverage without deleting existing fork tests.

**Исходное сообщение commit**

```
A plan that fills the card and the RAM with every expert and leaves nothing for the SSD wrote two caps equal to the plan. The engine counts its experts
a little differently (and the SSD-streaming mode takes a 65-slot ring out of the RAM cap), so on an RX 7900 XT with SQ-20 (12.53 + 2.08 GiB, 15.68 GB)
47 experts ended up on the SSD and the engine printed "GPU+SSD streaming active". The RAM cap of such a plan now gets max(0.75 GiB, 5% of the experts)
of room, bounded by the free RAM the planner was given. Plans with an SSD tier and plans that hold every expert in the card are unchanged.

Measured on boxia (RX 7900 XT, SQ-20, ctx 32768, 2 slots): RAM cap 2.08 streams 47 experts, 2.25 streams 16, 2.40 and above stream none; the
decode rate moves 38.4 -> 39.8 tok/s only. The rest of the gap to 0.2.20 (46.4) is the card cap (12.53 against 13.20 GiB), not this.

For 0.2.21.1 the room is written for the HIP backend only (the one it was measured on): CUDA, Metal, SYCL and CPU keep the caps they always had.
Taken from 74d9503b2 with that restriction and a test for it.
```
