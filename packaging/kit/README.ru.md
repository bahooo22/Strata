# Портативный комплект для inference с длинным контекстом (Strata + llama.cpp)

Одна сборка двух движков, которая сама смотрит на ваше железо и сама подбирает окно и
параметры. Все числа в ней — из замеров конкретного стенда (RTX 3060 Ti 8 ГБ, 4 ядра,
31.87 ГиБ ОЗУ, модели на SSD), а не из общих рассуждений; где замера нет, комплект говорит
об этом словами «это расчёт по формуле».

Моделей внутри архива нет. Комплект ничего не пишет вне своей папки.

## Быстрый старт

1. Распакуйте архив в любую папку (путь без кириллицы желателен, но не обязателен).
2. Дважды кликните `START.bat`.
3. На вопрос вставьте путь к файлу `.gguf` (можно перетащить файл на значок `START.bat`).

Комплект покажет четыре шага и попросит подтвердить запуск:

| шаг | что делает | файл |
|---|---|---|
| 1 | снимает железо: GPU, видеопамять, архитектуру, ядра, ОЗУ, тип диска под моделью, HAGS, MSI | `kit\detect.py` |
| 2 | сравнивает машину с нашей базой и говорит, что на ней не получится | `kit\classify.py` |
| 3 | по заголовку `.gguf` и классу железа считает максимальное окно и параметры | `kit\recommend.py` |
| 4 | запускает сервер и открывает адрес в браузере (флаг `-NoBrowser` не открывает) | `kit\start.ps1` |

Другие способы запуска:

```
START.bat model.gguf                     то же, но без вопроса о пути
START.bat model.gguf -DryRun             напечатать строку запуска и ничего не запускать
START.bat model.gguf -Yes                запустить без подтверждения
START.bat -FakeConfig 16g.json -Gguf model.gguf -DryRun
                                         подбор для чужого железа, не выключая своё
```

Полезно проверить комплект до первого реального запуска:

```
python kit\detect.py --selftest
python kit\classify.py --selftest
python kit\recommend.py --selftest
```

Нужен Python 3 (мы проверяли на 3.14); внешних зависимостей нет — только стандартная
библиотека. Если Python доступен как `py` — `py kit\detect.py --selftest`. Каждый из трёх
файлов умеет работать отдельно: `--out файл.json` записывает результат, `--json` печатает
машинный вывод.

## Что именно подбирается

Для Страты: размер окна, `--att-mb`, `--vram-reserve-mib`, super-chunk N, тип KV-кэша, MTP.
Для llama.cpp: окно, `--n-cpu-moe`, `-ub`, `-b`, `-fa`, число потоков. Порт Страты — 8082,
llama — 8081.

Окно считается по слагаемым видеопамяти: KV-кэш (байт на токен берётся из заголовка `.gguf`)
плюс attention-буфер, плюс запас, плюс состояние линейных слоёв, плюс (для llama) веса на GPU
при данном `--n-cpu-moe`. Шаг лесенки (64k, 80k, 96k, 128k, 160k) проходит, если сумма влезает.

Контроль честности: на нашей базе формула обязана воспроизвести замеренную лесенку с точностью
до одной ступени — это один из контролей в `recommend.py --selftest`.

## Модель, для которой подобраны параметры

`kit\models.json` — шесть замеренных моделей. У каждой строки есть ссылка на скачивание
(`hf_url`), проверенная по HEAD-запросу и совпадению размера, и первичник замера
(`src` — файл и строка таблицы). Если ваша модель не из этого списка, комплект подберёт
параметры по формуле и прямо скажет: «модели нет в реестре замеренных».

## Как читать предупреждения

Код возврата любого шага:

- `0` — verdict дан, замечаний нет;
- `1` — verdict дан с предупреждениями (текст напечатан; запуск возможен, но ожидайте
  медленного старта или меньшее окно);
- `2` — проверка не состоялась: битый вход, нет GPU, GGUF без метаданных. Это не «всё хорошо»,
  а «мерить было нечем».

Классы машины (`classify.py`) — по сравнению с нашей базой:

| вердикт | что значит |
|---|---|
| мощнее нашей базы | запас ≥ 1.5× по памяти; можно пробовать окно выше замеренного |
| не ниже нашей базы | ±5 %; все профили переносимы один в один |
| ниже нашей базы | что-то одно заметно меньше; часть окон не влезет |
| сильно ниже нашей базы | комплект предупреждает и перечисляет, чего не будет |

Тексты предупреждений и их смысл:

- «длинные окна (128k+) и MoE с CPU-экспертами в такую память не влезают» — упирается в видеопамять;
- «часть экспертов останется на диске, старт модели и прогон окна замедлятся» — мало ОЗУ;
- «CPU-эксперты (--n-cpu-moe) станут узким местом» — мало ядер;
- «загрузка модели с HDD измерялась только как ухудшение, не как профиль» — модель на HDD:
  наши профили снимались с SSD, время старта будет другим;
- «готового cubin для этой архитектуры в комплекте нет» — вашей архитектуры видеокарты нет среди
  собранных; расчёт идёт через PTX-JIT (медленный старт, непроверенный результат). Этот список
  берётся не из константы, а из `elf-proof.json` рядом с `kit\` — из доказательства по факту сборки.

## Какие конфигурации поддержаны

- Windows 10/11 x64, PowerShell 5.1 (оболочка комплекта — системная, pwsh 7 не нужен);
- видеокарты NVIDIA с архитектурой `sm_86`, `sm_89` либо `sm_120` — это Ampere (3060 Ti и
  родственники), Ada (4090, 4060 Ti 16G) и Blackwell (5080, 5090). Точный список собранных
  архитектур — в `elf-proof.json`, он же основание для предупреждения выше;
- драйвер, способный запустить CUDA 13 runtime (поставлен вместе с комплектом: `cublas64_13.dll`,
  `cublasLt64_13.dll`);
- модель в формате GGUF, помещающаяся в ОЗУ вместе с KV-кэшем подобранного окна.

## Вес

Полная версия (с CUDA-рантаймом) и тонкая (`-NoCudaRuntime`, cublas не едет) различаются
примерно на 488 МиБ — это `cublas64_13.dll` плюс `cublasLt64_13.dll`. Фактические замеры папки и
архива — в `kit-weight.json` рядом с этим файлом; он создаётся упаковщиком при каждой сборке
архива, поэтому число в нём всегда соответствует этому архиву.

## Как собрать комплект самому

Нужны pwsh 7, CMake, Ninja, MSVC и набор CUDA 13.3. Из корня стенда:

```
pwsh -File harness\scripts\build_kit.ps1 -Engines strata,llama -Arch "86;89;120"
pwsh -File harness\scripts\pack_kit.ps1                      # полная версия
pwsh -File harness\scripts\pack_kit.ps1 -NoCudaRuntime       # тонкая
```

Точка с запятой в списке архитектур обязательна в кавычках: без них оболочка разрезает аргумент.

`build_kit.ps1` пишет три меры в `dist\gpu-infer-kit`: `build-measure.json` (время и код возврата
настройки и сборки по каждому движку), `elf-proof.json` (какие cubin действительно лежат внутри
бинарников — снимается через `cuobjdump --list-elf`) и `runtime-deps.json` (замыкание зависимостей
через `dumpbin /imports`). `pack_kit.ps1` перед тем, как назвать архив готовым, проверяет: что все
обязательные файлы на месте, что в текстовых файлах дерева не осталось абсолютных путей с литерой
диска - ни в форме «литера, косая черта, дерево», ни в форме «литера, обратный слэш, дерево»
(JSON и CMake пишут и так, и удвоенным обратным слэшем перед именем файла), что меры читаются как
JSON без BOM, что собранные архитектуры покрывают заявленные, что зависимости замкнуты, что архив
открывается и что внутри нет моделей. Каждый контроль падает с внятной причиной; отсутствие
контроля — тоже провал, а не успех.

`-SelfTest` у обоих скриптов прогоняет контроли без сборки и без железа.

## Автоматика: что собирается и публикуется в GitHub Actions

CI-варианты тех же скриптов лежат в `packaging\kit\ci\` и вызываются только параметрами
(`-StrataSrc`, `-LlamaSrc`, `-GgmlDir`, `-Cuda`, `-Out`): прогон не знает путей стенда и не может
«случайно» собрать то, что работает дома и падает в Actions. Отсутствие обязательного параметра —
отказ с кодом 2, а не сборка вполовину.

Вход самоконтролей этих скриптов — pwsh 7, тот самый, которым их зовёт Actions. Windows PowerShell
5.1 перестал быть отдельной историей: тестовое дерево `pack_kit` строится той же записью, что и
реальные меры (`[System.IO.File]::WriteAllText` с `UTF8Encoding($false)`), потому что
`-Encoding utf8NoBOM` у `Set-Content` появился только в PowerShell 6+ и на 5.1 дерево не создавалось
вовсе - четыре контроля падали на несозданном дереве, а два из них ждали НОЛЬ находок и проходили
вхолостую (прежний вердикт этого входа - `ok=69 bad=4`). После правки оба входа дают одно и то же:
`pack_kit` 89/0 и `build_kit` 117/117 и на pwsh 7, и на 5.1 (замер 13.11, по одному прогону
каждого входа). Не парсится на 5.1 по-прежнему только `install_cuda_redist.ps1`
(строка 89): исходник лежит в UTF-8 без BOM, и 5.1 читает его как OEM. Это граница входа, а не
регрессия упаковки: Actions зовёт все три скрипта pwsh-ем, а реальный путь упаковки от оболочки не
зависел и прежде - меры пишутся `WriteAllText`, а не `-Encoding`. Отдельная разница входов -
round-trip JSON: `ConvertTo-Json` пишет Double `3321.0` как `3321`, и `ConvertFrom-Json` в 5.1
возвращает Int32, тогда как pwsh - Double; `Chk` в `build_kit.ps1` сравнивает дробные как числа при
любых типах и печатает типы в сообщении FAIL, чтобы равные значения не сравнивались строками.

- `kit-build.yml` (этот форк, запуск только по требованию: Actions → «Kit build (Strata CUDA
  servers)» → Run workflow, вход `arch` с дефолтом 86). Компиляция привязана к push быть не может:
  прогон тянет тулчейн CUDA и полную сборку движка, а проверять состав и маркеры нужно точечно.
  Первый job — шесть самоконтролей без тулчейна и без
  исходников: `-SelfTest` у build_kit, pack_kit и install_cuda_redist, плюс `patch_markers.py
  --selftest`, `kit_dll_deps.py --selftest` и `verify_zip.sh --selftest`. Тем же pwsh-шагом, сразу
  после цикла selftest'ов, вызывается `pack_kit.ps1 -TextGate` по дереву `packaging/kit`: он меряет не
  контроли, а сами входы - девять текстовых файлов манифеста, и тоже обходится без тулчейна и без
  компиляции. Второй job — CUDA 13.3.1 из
  redist-архивов (закреплённый sha256 на каждый архив, каталог загрузок в actions/cache), сборка
  `strata.exe` и `strata-q36.exe` на архитектуре 86 и гейт маркеров по байтам обоих exe.
- `kit-build-cuda.yml` (форк llama.cpp, так же только по требованию, с ветки `kit-all-sync`) — то же
  для сборки llama.cpp: скрипты и
  реестр маркеров берутся отдельным checkout из этого форка, потому что копия разошлась бы при
  первой же правке; `-Engines llama`, затем гейт по ggml-base.dll, ggml-cuda.dll и llama.dll.
- `kit-release.yml` (этот форк, публикация релиза по тегу или ручной прогон с тегом) — комплект
  целиком: оба движка ОДНИМ прогоном (`-Engines 'strata;llama'`) на `86;89;120`, потому что только
  парный прогон пишет объединённые build-measure.json и elf-proof.json, которые читает упаковщик;
  далее гейт маркеров обоих движков, реестр нативных зависимостей семью бинарниками, упаковка,
  формат-гейт архива по байтам (заголовок PK и EOCD) и загрузка ассетом в уже созданный релиз.
  Без тега остаётся артефактом прогона. Загружает ассет `gh`-ом, а он НЕ наследует автоматический
  токен прогона: шаг обязан получить `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (права `contents: write`
  в workflow уже объявлены). Без этой строки шаг падает последним - то есть после двухчасовой
  сборки - с текстом «set the GH_TOKEN environment variable». Пустой токен отдельным гейтом даёт
  rc=2 и явную причину, чтобы отказ читался как «публикация не состоялась», а не как «патчей нет».
  Гейт переносимости текстовых входов (`pack_kit.ps1 -TextGate` по исходникам `packaging/kit`) в этом
  workflow тоже отдельный дешёвый шаг - он стоит раньше проверки релиза и тем более раньше тулчейна.
  Существует ли релиз под ассет, проверяется первым дешёвым шагом, ещё до тулчейна CUDA: тем же
  `gh release view` с `GH_TOKEN` прогона. Пустой тег - «публикация не требуется», найденный релиз -
  «ассет доедет в него», отсутствующий - отказ за секунды с подсказкой создать релиз и не начавшейся
  компиляцией. Без гейта тот же отказ приходил последним шагом, после двухчасовой сборки; релизов
  в форке на 13.11 не было ни одного (0 при полностью унаследованном от апстрима списке тегов), то
  есть сценарий не гипотетический.

До пуша приёмка остаётся офлайн-мерой из двух частей. Первая - job `ci-gates` на чистом
tree-экспорте (`git archive main packaging/kit | tar -x`, без `.git` и без путей стенда):
`build_kit` 117/117 контролей, `pack_kit` 89/0, `install_cuda_redist` 27/0,
`patch_markers --selftest` 44/0, `kit_dll_deps --selftest` 14/0, `verify_zip --selftest` 6/0
(снято 13.11 одним прогоном обвязки). Вторая - гейт маркеров
на бинарниках стенда: 24/24 маркера Страты по 12 коммитам и 5/5 у llama.cpp по 3. Плюс статический
аудит трёх workflow: он ловит дефекты класса `GH_TOKEN` до начала долгого прогона, контроль самой
меры (шесть зарытых поломок и контроль ложной тревоги) даёт 7/7, а по трём файлам чист с одним
предупреждением - сборка llama.cpp берёт CI-скрипты плавающим `ref: main`, это цена одного источника
истины, а не забытый пин.

Три дефекта нашёл только живой релизный прогон 43345549955 (13.11, ветка репетиции `kit-ci-live`
на коммите `722299be`, `86;89;120`, тулчейн 13.3.1): сборка Страты 18,6 + 1147,8 с и llama
8,8 + 2249,9 с, обе метки `build_kind` - «холодная сборка» при нулях объектов до прогона,
гейт маркеров зелёный на обоих движках (24/24 и 5/5), а прогон всё равно упал.

- `rc(kit_dll_deps)=1`: `llama-common.dll` и `llama-server-impl.dll` импортировали
  `libssl-3-x64.dll` и `libcrypto-3-x64.dll`. Причина в дефолте `LLAMA_OPENSSL=ON`
  (`CMakeLists.txt:145` пина): образ раннера OpenSSL нашёл и слинковал, а стенд - нет
  (`OPENSSL_INCLUDE_DIR-NOTFOUND` в CMakeCache от 12.11), поэтому на стенде импорт-таблицы чисты и
  дефект не виден ни одной местной меркой. Сборка llama теперь идёт с `-DLLAMA_OPENSSL=OFF`, а
  контроль `openssl в llama выключён` держит этот флаг в тексте конфигурации; контроль - не подмена
  прогона, он падает, если флаг кто-то уберёт. Возить чужие dll в комплекте нельзя: их версия
  зависела бы от образа раннера, тогда как весь остальной комплект пинован sha256, а HTTPS комплекту
  не нужен - модели локальные.
- Артефакт сборки llama.cpp содержал 4 бинарника из 9, которые производит сборка: обёртка
  `llama-server.exe` без `llama-server-impl.dll` и `llama-common.dll` не запускается, а `ggml.dll` и
  `ggml-cpu.dll` зовёт из неё `ggml-base.dll`. Артефакт сборки называют набором серверов, и он
  обязан быть набираемым, а не списком трёх носителей маркеров. Класс закрыт гейтом наличия каждого
  названного файла, а не флагом: первичник `actions/upload-artifact` (`src/upload/upload-artifact.ts:31`)
  включает `if-no-files-found` только на пустое множество, а поиск у него один глоб на все пути сразу
  (`src/shared/search.ts:82-91`) - при 4 файлах из 9 множество непустое и флаг молчит. Список набора
  живёт в `env.ARTIFACT_FILES`, и им же кормится `path:` шага: вторая копия списка была бы ровно этим
  дефектом. Пустой список даёт rc=2 («мерять нечего»), а не зелёное «0 файлов на месте». Приёмка меры -
  исполнением настоящего текста шага из YAML на синтетическом дереве (13.11): 16/16, саботажи «исчез
  1 из 9» и «опечатка в каталоге» краснеют с именем файла, пустой список даёт rc=2, контроль ложной
  тревоги зелёный. Живые прогоны подтвердили гейт в обоих workflow сборки: Страта - `43367282553` (пуш в
  `main` на коммите `71f5e49a`, 13.11, job 04:42:51Z - 04:56:24Z, 813 с; сам шаг гейта
  04:56:13Z - 04:56:14Z) печатает «набор артефакта: 3 файлов на месте», llama - `43367290681`
  (пуш в `kit-all-sync`, 13.11, job 04:42:56Z - 05:08:45Z, 1549 с; сам шаг гейта 05:08:36Z) печатает
  «набор артефакта: 9 файлов на месте»; оба зелёные. Сверка названных путей с числами в тех же логах
  (`kit418_artifact_count.py`) даёт `[4, 3]` против `[4, 3]` и `[4, 9]` против `[4, 9]` при нуле
  «нет файлов», rc=0 на обоих прогонах.
- `strata_kq.dll` не было ни в комплекте, ни в артефактах, и прежние гейты этого не видели: её
  грузит код (`LoadLibraryA` рядом с движком, `src/prefill/mmq_kq_loader.cpp:57-70`, имя -
  `include/strata/prefill/mmq_kq_abi.hpp:9`), поэтому её нет ни в одной импорт-таблице. Её
  отсутствие означало молчаливую деградацию: K-quant-эксперты промпта уходили бы в FP16-путь, а
  сборка осталась бы зелёной. Проверено на стендовом бинарнике: `kit_dll_deps` даёт по нему ровно один импорт -
  `KERNEL32.dll` (CUDA-рантайм линкован статически, `cmake/backends/cuda.cmake`), то есть в списке
  релизного гейта она не из-за трудных зависимостей, а из-за способа загрузки.

Класс «сборка произвела, а комплект не взял» закрыт меркой замыкания набора в `pack_kit`: множество
exe/dll, которые сборка действительно произвела (плоский скан корня Страты и `llama\bin`: под
деревом лежат `CMakeFiles\**\*.exe`, и рекурсивный обход дал бы ложные находки), сверяется с
ключами `bin\*` манифеста, а находка — отказ rc=2 со списком файлов. Отпуск (`$BIN_WAIVERS`)
обязан иметь причину в самом словаре: единственный там `test-cuda-upload-stream.exe` появляется
только при `LLAMA_BUILD_TESTS=ON`, а CI собирает с `OFF`. Пустое или несуществующее дерево — тоже
rc=2, а не «ноль находок». Метка `bin\strata_kq.dll` добавлена в манифест, в список обязательных
файлов формат-гейта (`verify_zip.sh`, контроль ложной тревоги - 12 обязательных вместо 11) и в
артефакт сборки Страты в `kit-build.yml`. Живая приёмка мерки (13.11, `pack_kit` вызван стендовым кодом на реальных
деревьях Страты и llama.cpp, через hardlink-зеркало - без копирования гигабайт и без правок
стенда): саботаж `orphan_probe.dll` даёт rc=2 с названным файлом, полный прогон - rc=0 и строку
«произведено 13 exe/dll, в bin\ манифеста 14, отпуск 1», архив - 810,0 МиБ и 26 записей с
`bin/strata_kq.dll`, формат-гейт на нём - зелёный, тонкий прогон без CUDA-рантайма - rc=0 и
«в bin\ манифеста 12, отпуск 1» (меньше манифест, та же замыкающая находка).

Четвёртый класс - текст самого комплекта - нашёл релизный прогон `43359812438` (13.11, ручной прогон
с ветки репетиции `kit-ci-live`): job 03:34:02Z - 05:07:07Z, 5585 с, из них 5454 с на компиляцию обеих
движков; упал он на шаге «Раскладка и упаковка комплекта» (35 с, 05:06:24Z - 05:06:59Z) со строкой
«ВНИМАНИЕ: в комплекте остались пути стенда (2)» и `rc(pack_kit)=1`, формат-гейт архива при этом
остался skipped. Находками оказались `README.en.md` и `README.ru.md` - тот самый текст, который этот
гейт и описывает: в него коммитом `aab79d10` был внесён абсолютный путь каталога одного из прежних
прогонов. README-пара физически едет в архив (`pack_kit.ps1:190`), а `Remove-StandPaths` чистит
только сайдкары-меры (`$SIDECARS`, `:732`) - значит документ обязан оставлять чистым автора, и
проверять это надо до компиляции, а не после неё.

Класс закрыт входом `pack_kit.ps1 -TextGate`. Перечень файлов берётся из того же `Get-Manifest`, что
и реальная упаковка: вторая копия списка была бы ровно тем дефектом, который закрывали для
`env.ARTIFACT_FILES`. Меряются текстовые расширения (`.py`, `.ps1`, `.bat`, `.json`, `.md`, `.txt`,
`.cmd`), находка печатается относительным именем файла и строкой, а отсутствующий каталог `-KitSrc`,
отсутствующий входной файл и пустое множество измеряемых файлов - отказ rc=2 («проверка не
состоялась»), а не «находок нет». Приёмка четырьмя входами (13.11): `-SelfTest` даёт
`ok=89 bad=0` (было 82/0, контролирующих вызовов в selftest стало 69 против 62), прогон по живому
дереву `packaging/kit` - rc=0 и строку «текстовые входы: путей стенда нет, проверено 9 файлов»,
саботаж
(копия дерева с подсаженным абсолютным путём) - rc=1 с названным относительным именем и без пути
копии в выводе, отсутствующий каталог - rc=2. Оба оболочечных входа, pwsh 7 и Windows PowerShell 5.1,
дают те же 89/0. Тот же вызов стоит в первом job `kit-build.yml` и отдельным дешёвым шагом релизного
прогона -
раньше тулчейна CUDA и раньше проверки релиза: прогон, который обязан упасть на этом классе, теперь
стоит секунды вместо 5585 с.

Формат строк лога - класс, который зелёная сборка не замечает: у `-f` приоритет выше, чем у `+`,
поэтому `"шаблон {0}" + "хвост {1}" -f а, б` подставляет аргументы только во второй кусок. Живой
прогон 12.11 (`build-strata.log` репетиции kit378) показал в строке меры Страты литеральные
`{0}`...`{4}`: JSON-меры остались целыми, а нечитаемыми стали именно те холодные числа, ради
которых метка `build_kind` и затевалась. Починены четыре таких места - строки мер strata и llama,
строка no-op и строка доказательства архитектур с суффиксом; соседние `pack_kit` и
`install_cuda_redist` той же меркой чисты (0 находок). Класс закрыт в `-SelfTest` двумя мерками:
текстовой по скрипту (с двумя саботажными входами и одним контролем ложной тревоги) и поведенческой
- та же склейка шаблонов со скобками и без неё. После правок - 117/117 на обоих входах (pwsh 7
и Windows PowerShell 5.1).

Пригодность индекса компонентов (`redistrib_<версия>.json`) меряется структурой: метка релиза
равна запрошенной и компонентов не меньше 20. Прежний байтовый порог «не меньше 50 000 Б»
отбраковывал живой полный индекс 13.3.1 весом 47 914 Б (замер 12.11), то есть job падал до первого
скачивания; возврат порога ловит `-SelfTest` того же скрипта отдельной проверкой по тексту кода.

Раскладка архивов сливается рекурсивно, а не переносится верхним слоем: каталоги компонентов
перекрываются (листинг 9 архивов 12.11: `bin` у 4 из 9, `include` у 6 из 9, `lib` у 3 из 9), а
перенос каталога на уже существующий каталог PowerShell кладёт его внутрь. Первый же живой прогон
12.11 при совпавших sha256 всех девяти архивов дал `bin\bin\x64\cublas64_13.dll` и
`include\include\cuda_runtime.h` — тулчейн был бы неполным, и это поймал только список
обязательных файлов. Самоконтроль скрипта проверяет слияние второго архива семью отдельными
проверками.

Гейт маркеров — то, что зелёная сборка доказать не может. Реестр
`packaging\kit\ci\patch-markers.json` снят 12.11 с настоящих бинарников: 24 маркера для Страты на
двух носителях (exe) и 5 для llama.cpp на трёх (dll). Маркеры покрывают 12 из 81 наших коммитов
Страты и 3 из 14 у llama.cpp: правки, не оставляющие в бинарнике читаемого имени (строковый
литерал или имя cuda-ядра из fatbin), гейт не видит — их по-прежнему проверяют паритетные замеры на
стенде. Пропавший маркер — код возврата 1 и красный прогон; отсутствующий носитель — код 2, то
есть «проверка не состоялась».

Два правила, без которых реестр врёт, проверены меркой и записаны в самом файле. Имя маркера
обязано отсутствовать в дереве базы апстрима: найденное в exe `--cache-type-k` ничего не доказывало
бы, потому что такой флаг есть и у стока. Поле `commit` — самый старый наш коммит, изменивший число
вхождений имени, то есть внедривший его: прежнее сопоставление брало коммит из выборки «имя
встречается в дереве» и перетягивало атрибуцию на позднейшее упоминание - у шести маркеров оно
вело на packaging-коммит 11.11 или на соседний по теме патч вместо коммита, который имя придумал.

В Actions не меряется то, для чего нужна видеокарта: запуск серверов с моделью и предельная цена
каждой архитектуры (`-SkipProbe`). Ограничения по времени опираются на холодные сборки: метка
`build_kind` в build-measure ставится по числу объектов целей в дереве сборки ДО прогона и различает
«холодная сборка», «частичная сборка» (прогрев после правки), «no-op» и «холодность не измерена»;
время прогрева цену полной компиляции не называет и лимиты не обосновывает.

Четыре холодных числа на трёх архитектурах, у каждого есть файл-носитель в стендовом
`dist\`: strata 1686.2 с
(`gpu-infer-kit-strata-cold3`: 160 компиляций и 14 линковок из плана 174, в логе выполнено 174 ребра
из 174, commit `0f37b86e`) и повтор того же состава 1774.1 с (`gpu-infer-kit-strata-cold`);
llama 3006.1 с (`gpu-infer-kit-llama-sync3`, commit `c8b1899f9`) и 3321.0 с
(`gpu-infer-kit-llama-cold`) — в обоих логах 330/330 рёбер и 315 компиляций из плана 330. Все четыре
прогона сделаны на одном составе архитектур: `CMakeCache.txt` деревьев
`engine-kit-kitall\build-kit-cold3` и `llama-kit\build-kit-cold` содержит `86;89;120`, а fatbin
бинарников тех же деревьев даёт 26 записей `sm_86`, 26 `sm_89`, 25 `sm_120` и 1 `sm_120a` в
`strata-q36.exe` и 27 `sm_86`, 32 `sm_89`, 43 `sm_120a` в `ggml-cuda.dll`. Поле `archs` в этих
measure-файлах пустое, а `build_kind` несёт прежнюю метку «полная компиляция»: снимки сделаны кодом
до правки метки холодности, поэтому и холодность, и состав доказаны логами и CMakeCache, а не
полями measure.

Четыре числа выше сняты на трёх архитектурах, а `kit-build.yml` собирает одну (86 по умолчанию) - это и
был последний незакрытый зазор в обосновании лимита. Он закрыт 13.11 прогоном на чистых клонах с
GitHub-remote обоих форков: тулчейн из redist-архивов, `ci/build_kit.ps1` вызван теми же
аргументами, что в настоящем прогоне, пробник архитектур выключен явно (`-SkipProbe`). strata - 751.6 с
компиляции после 13.9 с настройки (носитель `gpu-infer-kit-strata-cold86`, коммит `11cbea3`,
160 компиляций и 14 линковок, в логе выполнено 174 ребра из 174); llama - 1370.2 с после 12.1 с
(`gpu-infer-kit-llama-cold86`, коммит `39628e5`, 315 компиляций и 14 линковок, 330 рёбер из 330).
У обоих measure-поля заполнены уже корректно: `archs` = `["86"]`, `build_kind` = «холодная
сборка», `prebuilt_objects` = 0 - холодность доказана самим полем, а не только CMakeCache.
`elf-proof` тех же прогонов даёт cubin ровно на 86: 28 записей `sm_86` в `strata-q36.exe`, 71 в
`strata.exe` и 149 в `ggml-cuda.dll`; гейт маркеров на этих бинарниках зелёный - strata 24/24 при
12 из 12 покрытых коммитах, llama 5/5 при 3 из 3, файлы `markers-*.json` лежат рядом с мерами.

Прежний вариант абзаца про четыре прогона держался на незакрытых мерках: strata 737.7 с
файла-носителя не имеет вообще (только stdout прогона и тела коммитов), а strata 712.6 с и
llama 2788.8 с — прогревы, 25+5 и 156+8 выполненных шагов вместо 174 и 330.

Отсюда и лимиты. Релизный прогон идёт 240 минут и собирает в одном дереве оба движка на 86, 89 и 120:
худшая из измеренных пар — 1774.1 + 3321.0 = 5095.1 с (84.9 минуты), пара одного и того же прогона —
1686.2 + 3006.1 = 4692.3 с (78.2 минуты); 240 минут — это в 2.8 раза больше худшей пары, остальное
уходит на тулчейн CUDA, упаковку и публикацию ассета. С 13.11 у этого лимита есть и прямая мера
в самом Actions: прогон 43345549955 на том же составе `86;89;120` дал 1147,8 с Страты и 2249,9 с
llama - 3397,7 с (56,6 минуты) чистого компилирования, и это полная цена сборки, потому что оба движка
тогда собрались целиком, а падение случилось позже, на гейте зависимостей; запас
14 400 / 3397,7 = 4,2 раза. `kit-build.yml` получает 180 минут и собирает одну архитектуру
(по умолчанию 86), и с 13.11 у неё есть прямая мера на том же составе: худший из двух
движков на 86 - llama 1370.2 с, отсюда запас 10 800 / 1370.2 = 7.9 раза, для strata 751.6 с - 14.4 раза.
Прежняя оценка держалась на трёхархитектурном прогоне 1774.1 с (запас в 6.1 раза) и была верхней
границей, а не измеренной ценой.

## Чего здесь нет

- моделей (архив не содержит ни одного `.gguf`);
- Linux и macOS;
- замеров на железе, отличном от нашей базы: предупреждение класса «ниже/сильно ниже» — это
  честная граница переносимости профилей, а не обещание тех же скоростей;
- MTP на окнах 64k и выше (измерено как ухудшение — в комплект не включён), и вообще всех
  отклонённых рычагов: их список с числами — в отчёте стенда `docs\reports`.
