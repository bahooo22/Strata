# Портативный комплект для inference с длинным контекстом (Strata + llama.cpp)

Одна сборка двух движков, которая сама смотрит на ваше железо и сама подбирает окно и
параметры. Все числа в ней — из замеров конкретного стенда (RTX 3060 Ti 8 ГБ, 4 ядра,
31.87 ГиБ ОЗУ, модели на SSD), а не из общих рассуждений; где замера нет, комплект говорит
об этом словами «это расчёт по формуле».

Моделей внутри архива нет. Комплект ничего не пишет вне своей папки.

## Быстрый старт

1. Распакуйте архив в любую папку (путь без кириллицы желателен, но не обязателен).
2. Дважды кликните `START.bat`.
3. На вопрос вставьте путь к файлу `.gguf` (можно перетащить файл на значок `START.bat`).

Комплект покажет четыре шага и попросит подтвердить запуск:

| шаг | что делает | файл |
|---|---|---|
| 1 | снимает железо: GPU, видеопамять, архитектуру, ядра, ОЗУ, тип диска под моделью, HAGS, MSI | `kit\detect.py` |
| 2 | сравнивает машину с нашей базой и говорит, что на ней не получится | `kit\classify.py` |
| 3 | по заголовку `.gguf` и классу железа считает максимальное окно и параметры | `kit\recommend.py` |
| 4 | запускает сервер и открывает адрес в браузере (флаг `-NoBrowser` не открывает) | `kit\start.ps1` |

Другие способы запуска:

```
START.bat model.gguf                     то же, но без вопроса о пути
START.bat model.gguf -DryRun             напечатать строку запуска и ничего не запускать
START.bat model.gguf -Yes                запустить без подтверждения
START.bat -FakeConfig 16g.json -Gguf model.gguf -DryRun
                                         подбор для чужого железа, не выключая своё
```

Полезно проверить комплект до первого реального запуска:

```
python kit\detect.py --selftest
python kit\classify.py --selftest
python kit\recommend.py --selftest
```

Нужен Python 3 (мы проверяли на 3.14); внешних зависимостей нет — только стандартная
библиотека. Если Python доступен как `py` — `py kit\detect.py --selftest`. Каждый из трёх
файлов умеет работать отдельно: `--out файл.json` записывает результат, `--json` печатает
машинный вывод.

## Что именно подбирается

Для Страты: размер окна, `--att-mb`, `--vram-reserve-mib`, super-chunk N, тип KV-кэша, MTP.
Для llama.cpp: окно, `--n-cpu-moe`, `-ub`, `-b`, `-fa`, число потоков. Порт Страты — 8082,
llama — 8081.

Окно считается по слагаемым видеопамяти: KV-кэш (байт на токен берётся из заголовка `.gguf`)
плюс attention-буфер, плюс запас, плюс состояние линейных слоёв, плюс (для llama) веса на GPU
при данном `--n-cpu-moe`. Шаг лесенки (64k, 80k, 96k, 128k, 160k) проходит, если сумма влезает.

Контроль честности: на нашей базе формула обязана воспроизвести замеренную лесенку с точностью
до одной ступени — это один из контролей в `recommend.py --selftest`.

## Модель, для которой подобраны параметры

`kit\models.json` — шесть замеренных моделей. У каждой строки есть ссылка на скачивание
(`hf_url`), проверенная по HEAD-запросу и совпадению размера, и первичник замера
(`src` — файл и строка таблицы). Если ваша модель не из этого списка, комплект подберёт
параметры по формуле и прямо скажет: «модели нет в реестре замеренных».

## Как читать предупреждения

Код возврата любого шага:

- `0` — verdict дан, замечаний нет;
- `1` — verdict дан с предупреждениями (текст напечатан; запуск возможен, но ожидайте
  медленного старта или меньшее окно);
- `2` — проверка не состоялась: битый вход, нет GPU, GGUF без метаданных. Это не «всё хорошо»,
  а «мерить было нечем».

Классы машины (`classify.py`) — по сравнению с нашей базой:

| вердикт | что значит |
|---|---|
| мощнее нашей базы | запас ≥ 1.5× по памяти; можно пробовать окно выше замеренного |
| не ниже нашей базы | ±5 %; все профили переносимы один в один |
| ниже нашей базы | что-то одно заметно меньше; часть окон не влезет |
| сильно ниже нашей базы | комплект предупреждает и перечисляет, чего не будет |

Тексты предупреждений и их смысл:

- «длинные окна (128k+) и MoE с CPU-экспертами в такую память не влезают» — упирается в видеопамять;
- «часть экспертов останется на диске, старт модели и прогон окна замедлятся» — мало ОЗУ;
- «CPU-эксперты (--n-cpu-moe) станут узким местом» — мало ядер;
- «загрузка модели с HDD измерялась только как ухудшение, не как профиль» — модель на HDD:
  наши профили снимались с SSD, время старта будет другим;
- «готового cubin для этой архитектуры в комплекте нет» — вашей архитектуры видеокарты нет среди
  собранных; расчёт идёт через PTX-JIT (медленный старт, непроверенный результат). Этот список
  берётся не из константы, а из `elf-proof.json` рядом с `kit\` — из доказательства по факту сборки.

## Какие конфигурации поддержаны

- Windows 10/11 x64, PowerShell 5.1 (оболочка комплекта — системная, pwsh 7 не нужен);
- видеокарты NVIDIA с архитектурой `sm_86`, `sm_89` либо `sm_120` — это Ampere (3060 Ti и
  родственники), Ada (4090, 4060 Ti 16G) и Blackwell (5080, 5090). Точный список собранных
  архитектур — в `elf-proof.json`, он же основание для предупреждения выше;
- драйвер, способный запустить CUDA 13 runtime (поставлен вместе с комплектом: `cublas64_13.dll`,
  `cublasLt64_13.dll`);
- модель в формате GGUF, помещающаяся в ОЗУ вместе с KV-кэшем подобранного окна.

## Вес

Полная версия (с CUDA-рантаймом) и тонкая (`-NoCudaRuntime`, cublas не едет) различаются
примерно на 488 МиБ — это `cublas64_13.dll` плюс `cublasLt64_13.dll`. Фактические замеры папки и
архива — в `kit-weight.json` рядом с этим файлом; он создаётся упаковщиком при каждой сборке
архива, поэтому число в нём всегда соответствует этому архиву.

## Как собрать комплект самому

Нужны pwsh 7, CMake, Ninja, MSVC и набор CUDA 13.3. Из корня стенда:

```
pwsh -File harness\scripts\build_kit.ps1 -Engines strata,llama -Arch "86;89;120"
pwsh -File harness\scripts\pack_kit.ps1                      # полная версия
pwsh -File harness\scripts\pack_kit.ps1 -NoCudaRuntime       # тонкая
```

Точка с запятой в списке архитектур обязательна в кавычках: без них оболочка разрезает аргумент.

`build_kit.ps1` пишет три меры в `dist\gpu-infer-kit`: `build-measure.json` (время и код возврата
настройки и сборки по каждому движку), `elf-proof.json` (какие cubin действительно лежат внутри
бинарников — снимается через `cuobjdump --list-elf`) и `runtime-deps.json` (замыкание зависимостей
через `dumpbin /imports`). `pack_kit.ps1` перед тем, как назвать архив готовым, проверяет: что все
обязательные файлы на месте, что в текстовых файлах дерева не осталось абсолютных путей с литерой
диска - ни в форме «литера, косая черта, дерево», ни в форме «литера, обратный слэш, дерево»
(JSON и CMake пишут и так, и удвоенным обратным слэшем перед именем файла), что меры читаются как
JSON без BOM, что собранные архитектуры покрывают заявленные, что зависимости замкнуты, что архив
открывается и что внутри нет моделей. Каждый контроль падает с внятной причиной; отсутствие
контроля — тоже провал, а не успех.

`-SelfTest` у обоих скриптов прогоняет контроли без сборки и без железа.

## Автоматика: что собирается и публикуется в GitHub Actions

CI-варианты тех же скриптов лежат в `packaging\kit\ci\` и вызываются только параметрами
(`-StrataSrc`, `-LlamaSrc`, `-GgmlDir`, `-Cuda`, `-Out`): прогон не знает путей стенда и не может
«случайно» собрать то, что работает дома и падает в Actions. Отсутствие обязательного параметра —
отказ с кодом 2, а не сборка вполовину.

Вход самоконтролей этих скриптов — pwsh 7, тот самый, которым их зовёт Actions: `pack_kit.ps1
-SelfTest` даёт на нём `ok=73 bad=0` (замер 12.11). Под Windows PowerShell 5.1 тот же прогон —
`ok=69 bad=4` (прежде было `ok=63 bad=3`; семь контроли добавлены фиксом переносимости, числа
сняты обоими входами на одном дереве). Четыре FAIL стоят на несостоявшемся входе, а не на упаковке:
тестовое дерево не создаётся, потому что `-Encoding utf8NoBOM` у `Set-Content` появился только в
PowerShell 6+, а `install_cuda_redist.ps1` в 5.1 не парсится вовсе (исходник в UTF-8 без BOM, и 5.1
читает его как OEM). Красное на этом входе значит «проверка не состоялась», а зелёное — не значит
ничего: два новых контроля ждут НОЛЬ находок и на несозданном дереве проходят вхолостую. Отдельная
разница входов — round-trip JSON: `ConvertTo-Json` пишет Double `3321.0` как `3321`, и
`ConvertFrom-Json` в 5.1 возвращает Int32, тогда как pwsh — Double; `Chk` в `build_kit.ps1`
сравнивает дробные как числа при любых типах и печатает типы в сообщении FAIL, чтобы равные значения
не сравнивались строками. Реальный путь упаковки от оболочки не зависит: меры пишутся
`[System.IO.File]::WriteAllText` с `UTF8Encoding($false)`, а не `-Encoding`.

- `kit-build.yml` (этот форк, пуш в `main`, задевший `src/`, `include/`, `cmake/`,
  `CMakeLists.txt` или `packaging/kit/`). Первый job — пять самоконтролей без тулчейна и без
  исходников: `-SelfTest` у build_kit, pack_kit и install_cuda_redist, плюс `patch_markers.py
  --selftest` и `verify_zip.sh --selftest`. Второй job — CUDA 13.3.1 из redist-архивов
  (закреплённый sha256 на каждый архив, каталог загрузок в actions/cache), сборка `strata.exe` и
  `strata-q36.exe` на архитектуре 86 и гейт маркеров по байтам обоих exe.
- `kit-build-cuda.yml` (форк llama.cpp, пуш в `kit-all-sync`) — то же для llama-ноги: скрипты и
  реестр маркеров берутся отдельным checkout из этого форка, потому что копия разошлась бы при
  первой же правке; `-Engines llama`, затем гейт по ggml-base.dll, ggml-cuda.dll и llama.dll.
- `kit-release.yml` (этот форк, публикация релиза по тегу или ручной прогон с тегом) — комплект
  целиком: обе ноги ОДНИМ прогоном (`-Engines 'strata;llama'`) на `86;89;120`, потому что только
  парный прогон пишет объединённые build-measure.json и elf-proof.json, которые читает упаковщик;
  далее гейт маркеров обеих ног, реестр нативных зависимостей шестью бинарниками, упаковка,
  формат-гейт архива по байтам (заголовок PK и EOCD) и загрузка ассетом в уже созданный релиз.
  Без тега остаётся артефактом прогона. Загружает ассет `gh`-ом, а он НЕ наследует автоматический
  токен прогона: шаг обязан получить `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (права `contents: write`
  в workflow уже объявлены). Без этой строки шаг падает последним - то есть после двухчасовой
  сборки - с текстом «set the GH_TOKEN environment variable». Пустой токен отдельным гейтом даёт
  rc=2 и явную причину, чтобы отказ читался как «публикация не состоялась», а не как «патчей нет».

До пуша приёмка остаётся офлайн-мерой из двух частей. Первая - job `ci-gates` на чистом
tree-экспорте (`git archive main packaging/kit | tar -x`, без `.git` и без путей стенда):
`build_kit` 109/109 контролей, `pack_kit` 73/0, `install_cuda_redist` 27/0,
`patch_markers --selftest` 28/0, `verify_zip --selftest` 6/0 (снято 13.11). Вторая - гейт маркеров
на бинарниках стенда: 24/24 маркера Страты по 12 коммитам и 5/5 в llama-ноге по 3. Плюс статический
аудит трёх workflow: он ловит дефекты класса `GH_TOKEN` до начала долгого прогона, контроль самой
меры (шесть зарытых поломок и контроль ложной тревоги) даёт 7/7, а по трём файлам чист с одним
предупреждением - llama-нога берёт CI-скрипты плавающим `ref: main`, это цена одного источника
истины, а не забытый пин.

Пригодность индекса компонентов (`redistrib_<версия>.json`) меряется структурой: метка релиза
равна запрошенной и компонентов не меньше 20. Прежний байтовый порог «не меньше 50 000 Б»
отбраковывал живой полный индекс 13.3.1 весом 47 914 Б (замер 12.11), то есть job падал до первого
скачивания; возврат порога ловит `-SelfTest` того же скрипта отдельной проверкой по тексту кода.

Раскладка архивов сливается рекурсивно, а не переносится верхним слоем: каталоги компонентов
перекрываются (листинг 9 архивов 12.11: `bin` у 4 из 9, `include` у 6 из 9, `lib` у 3 из 9), а
перенос каталога на уже существующий каталог PowerShell кладёт его внутрь. Первый же живой прогон
12.11 при совпавших sha256 всех девяти архивов дал `bin\bin\x64\cublas64_13.dll` и
`include\include\cuda_runtime.h` — тулчейн был бы неполным, и это поймал только список
обязательных файлов. Самоконтроль скрипта проверяет слияние второго архива семью отдельными
проверками.

Гейт маркеров — то, что зелёная сборка доказать не может. Реестр
`packaging\kit\ci\patch-markers.json` снят 12.11 с настоящих бинарников: 24 маркера для Страты на
двух носителях (exe) и 5 для llama-ноги на трёх (dll). Маркеры покрывают 12 из 81 наших коммитов
Страты и 3 из 14 в llama-ноге: правки, не оставляющие в бинарнике читаемого имени (строковый
литерал или имя cuda-ядра из fatbin), гейт не видит — их по-прежнему проверяют паритетные замеры на
стенде. Пропавший маркер — код возврата 1 и красный прогон; отсутствующий носитель — код 2, то
есть «проверка не состоялась».

Два правила, без которых реестр врёт, проверены меркой и записаны в самом файле. Имя маркера
обязано отсутствовать в дереве базы апстрима: найденное в exe `--cache-type-k` ничего не доказывало
бы, потому что такой флаг есть и у стока. Поле `commit` — самый старый наш коммит, изменивший число
вхождений имени, то есть внедривший его: прежнее сопоставление брало коммит из выборки «имя
встречается в дереве» и перетягивало атрибуцию на позднейшее упоминание - у шести маркеров оно
вело на packaging-коммит 11.11 или на соседний по теме патч вместо коммита, который имя придумал.

В Actions не меряется то, для чего нужна видеокарта: запуск серверов с моделью и предельная цена
каждой архитектуры (`-SkipProbe`). Ограничения по времени опираются на холодные сборки: метка
`build_kind` в build-measure ставится по числу объектов целей в дереве сборки ДО прогона и различает
«холодная сборка», «частичная сборка» (прогрев после правки), «no-op» и «холодность не измерена»;
время прогрева цену полной компиляции не называет и лимиты не обосновывает.

Снятых холодных чисел четыре, у каждого есть файл-носитель в стендовом `dist\`: strata 1686.2 с
(`gpu-infer-kit-strata-cold3`: 160 компиляций и 14 линковок из плана 174, в логе выполнено 174 ребра
из 174, commit `0f37b86e`) и повтор того же состава 1774.1 с (`gpu-infer-kit-strata-cold`);
llama 3006.1 с (`gpu-infer-kit-llama-sync3`, commit `c8b1899f9`) и 3321.0 с
(`gpu-infer-kit-llama-cold`) — в обоих логах 330/330 рёбер и 315 компиляций из плана 330. Все четыре
прогона сделаны на одном составе архитектур: `CMakeCache.txt` деревьев
`engine-kit-kitall\build-kit-cold3` и `llama-kit\build-kit-cold` содержит `86;89;120`, а fatbin
бинарников тех же деревьев даёт 26 записей `sm_86`, 26 `sm_89`, 25 `sm_120` и 1 `sm_120a` в
`strata-q36.exe` и 27 `sm_86`, 32 `sm_89`, 43 `sm_120a` в `ggml-cuda.dll`. Поле `archs` в этих
measure-файлах пустое, а `build_kind` несёт прежнюю метку «полная компиляция»: снимки сделаны кодом
до правки метки холодности, поэтому и холодность, и состав доказаны логами и CMakeCache, а не
полями measure.

Прежние числа этого абзаца держались на незакрытых мерках: strata 737.7 с файла-носителя не имеет
вообще (только stdout прогона и тела коммитов), а strata 712.6 с и llama 2788.8 с — прогревы, 25+5
и 156+8 выполненных шагов вместо 174 и 330.

Отсюда и лимиты. Релизный прогон идёт 240 минут и собирает в одном дереве обе ноги на 86, 89 и 120:
худшая из измеренных пар — 1774.1 + 3321.0 = 5095.1 с (84.9 минуты), пара одного и того же прогона —
1686.2 + 3006.1 = 4692.3 с (78.2 минуты); 240 минут — это в 2.8 раза больше худшей пары, остальное
уходит на тулчейн CUDA, упаковку и публикацию ассета. Пуш-джоба получает 180 минут и собирает одну
архитектуру (по умолчанию 86), поэтому 1774.1 с трёхархитектурного прогона служит ей верхней оценкой:
запас в 6.1 раза. Отдельного холодного замера на 86 с файлом-носителя нет, и цена llama-ноги
на 86 не замеряна.

## Чего здесь нет

- моделей (архив не содержит ни одного `.gguf`);
- Linux и macOS;
- замеров на железе, отличном от нашей базы: предупреждение класса «ниже/сильно ниже» — это
  честная граница переносимости профилей, а не обещание тех же скоростей;
- MTP на окнах 64k и выше (измерено как ухудшение — в комплект не включён), и вообще всех
  отклонённых рычагов: их список с числами — в отчёте стенда `docs\reports`.
